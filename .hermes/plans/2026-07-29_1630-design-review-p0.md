### Step 2: 1.1 文件协议扩展

**变更**：
- `docs/api/01-protocol.md` 中 `POST /api/v1/files` 响应体加 `source` / `modality` / `owner_user_id` 字段
- 新增章节"文件归属与生命周期"

**文档新增**：

```json
{
  "id": "file_xxx",
  "source": "user_upload" | "ai_generated",
  "modality": "image" | "audio" | "video" | "document",
  "owner_user_id": "user_xxx",
```

### Step 3: 1.2 Job 异步任务协议

**变更**：
- `docs/api/01-protocol.md` 新增"3. 异步任务（Job）"章节
- `docs/architecture/00-overview.md` 在 Modality 列表加异步任务说明
- `docs/roadmap/04-extensibility.md` Step 3 的 Provider 接口从流式改为 Job 提交

**文档新增**：

```
POST   /api/v1/jobs              → 提交任务，返回 job_id
GET    /api/v1/jobs/{id}         → 查状态
GET    /api/v1/jobs/{id}/result  → 拿结果
DELETE /api/v1/jobs/{id}         → 取消
GET    /api/v1/jobs              → 列表
```

**Job 状态机**：
```
pending → running → (succeeded | failed | cancelled)
                 ↑↓
              paused (可选，2.0+)
```

**响应 schema**：

```json
{
  "id": "job_xxx",
  "type": "music.generate",
  "status": "running",
  "progress": 0.45,
  "result_file_ids": [],
  "error": null,
  "created_at": "...",
  "updated_at": "..."
}
```

**流式进度**（SSE，可选）：
```
GET /api/v1/jobs/{id}/events
data: {"status": "running", "progress": 0.45}
data: {"status": "running", "progress": 0.67}
data: {"status": "succeeded", "result_file_ids": ["file_xxx"]}
data: [DONE]
```

**为什么 1.0 就定义**：2.0 加音乐/视频/图片全部异步，现在定义=一次到位；2.0 加时只写 Provider 实现，不动协议。

**验证**：mkdocs build --strict 通过

### Step 4: 2.3 分层限流

**变更**：
- `docs/backend/02-provider.md` 新增"限流策略"章节
- `docs/api/01-protocol.md` 错误响应增加 `Retry-After` header 描述
- 配置项：routing.rate_limit.*

**文档新增**：

```yaml
rate_limit:
  user:
    requests_per_minute: 100
    burst: 20
  provider:  # 限到 Provider 公开 RPM × 0.8
    openai: 4500      # gpt-4o 公开 5000/min
    doubao: 2400
    deepseek: 2400
    kimi: 2400
  global:
    concurrent_streams: 500
```

**响应头**：
```
HTTP/1.1 429 Too Many Requests
Retry-After: 30
X-RateLimit-Limit: 100
X-RateLimit-Remaining: 0
```

**后端实现**（架构层描述，不写代码）：
- `golang.org/x/time/rate` 令牌桶
- 三层独立桶：用户 / Provider / 全局并发
- 命中后等 0.3s 再判（避免 burst）
- 错误码：`user_rate_limit` / `provider_rate_limit` / `system_overload`

**验证**：mkdocs build --strict 通过

### Step 5: 2.2 SSE 断线重连

**变更**：
- `docs/api/01-protocol.md` SSE 协议加 chunk 序号 + 续传端点
- `docs/frontend/03-web.md` useSSE composable 加断线重连
- `docs/backend/02-provider.md` 加流缓存 + 续传实现

**协议扩展**：

```
data: {"id": "chatcmpl-xxx", "chunk_index": 0, "delta": "Go "}
data: {"id": "chatcmpl-xxx", "chunk_index": 1, "delta": "interface "}
...
data: {"id": "chatcmpl-xxx", "chunk_index": 42, "delta": "...", "finish_reason": "stop"}
data: [DONE]
```

**续传端点**：
```
GET /api/v1/chat/completions/{id}?from_chunk=<index>
```
- Master 缓存最近 5 分钟的 chunk 序列（in-memory LRU，默认 1000 条 / chat）
- `from_chunk=N` 表示从 N 开始重发（包含 N），0 表示全量重发
- 缓存过期或 chat 太久 → 410 Gone

**前端 useSSE 行为**：
1. 连接断开时记录最后 chunk_index
2. 立即重试 1 次（短抖动）
3. 仍失败 → GET 续传端点
4. 续传失败 → 提示用户"对话已断开，建议开启新对话"
5. 移动端 network change 时主动重连

**验证**：mkdocs build --strict 通过

### Step 6: 3.2 错误信息本地化

**变更**：
- `docs/api/01-protocol.md` 错误响应增加 `user_message` 字段（可选）+ 推荐前端 i18n 映射
- `docs/frontend/03-web.md` 新增"错误码 i18n 映射表" + 接入 useSSE/useChat 的方式

**协议扩展**：

```json
{
  "error": {
    "code": "provider_rate_limit",
    "message": "豆包 API 限流，请稍后重试",     // 后端原始 message（开发用）
    "user_message_key": "errors.provider_rate_limit",  // 前端 i18n key
    "retry_after": 30,
    "provider": "doubao"
  }
}
```

**前端映射示例**（`src/i18n/zh.ts`）：

```ts
export const errors = {
  auth_missing: '请先登录',
  auth_invalid: '登录已过期，请重新登录',
  model_not_found: '该模型暂不可用',
  provider_rate_limit: '服务商繁忙，请稍后重试',
  upstream_timeout: '网络超时，请检查连接',
  user_rate_limit: '请求过于频繁，请稍后重试',
  internal_error: '服务暂时不可用，请稍后重试',
}
```

**关键**：
- 后端只发 `code` + 可选 `user_message_key`
- 前端按 lang 渲染，前端 i18n key 找不到时降级用 `message`
- 1.0 支持中/英，2.0 扩展更多语言

**验证**：mkdocs build --strict 通过

### Step 7: 3.1 渐进式 onboarding

**变更**：
- `docs/frontend/03-web.md` 新增"Onboarding 流程"章节
- `docs/architecture/00-overview.md` 在非功能需求加"首次使用门槛 ≤ 30 秒"

**Onboarding 流程**：

```
1. 用户首次进入 → 看到 "选择你想用的 AI" 卡片
   [豆包] [OpenAI] [DeepSeek] [Kimi]
   ↓ 选了 1 个
2. 引导去配 Key 页面（不是设置页浮窗，是 onboarding 流内）
   输入 Key → 验证 → 成功
   ↓
3. 立刻进聊天页，模型选择器预选刚配的那个
4. 顶栏非干扰提示："再配 1 个可解锁对比模式"（P1，可选）
```

**模型选择器分级**：
- 一级：已配 Key 的模型（亮）
- 二级：未配 Key 的模型（半透明，hover 显示"点此配 Key"）
- 不在选择器里：列出但带锁图标

**关键原则**：
- 1 个 Key 就能开始用，**不是 0 警告也不是 N 警告**
- onboarding 可跳过（高级用户）
- onboarding 状态存 localStorage，"已配过"不再展示

**验证**：mkdocs build --strict 通过

## 6. 风险与权衡

- **协议层变更频率**：本批在 1.0 上线前定义，1.0 上线后严格按 P2 演进策略走
- **Job 协议 1.0 不实现**：纯文档落地，1.0 任务拆分加 1 条 "Phase X: Job 基础设施（占位）"
- **SSE 缓存内存开销**：1.0 用户少，1000 chunk × 50 字节 ≈ 50KB/chat，可接受；2.0 再做 LRU 调优
- **错误 i18n 双源**：1.0 后端只发 code，前端 i18n；如某些错误要后端动态生成文案（比如"豆包返回了 502"），保留 `message` 字段作为 fallback
